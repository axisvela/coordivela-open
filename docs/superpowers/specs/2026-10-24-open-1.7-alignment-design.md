# COORDIVELA-open 1.7 Alignment Design

**Date:** 2026-10-24

**Goal:** Align `COORDIVELA-open` with Core `1.7.0`, remove contract/SDK drift,
and publish complete signed `v1.7.0` release artifacts under `releases/v1.7.0/`.

## Context

Core is at `1.7.0` and exposes coordination-loop routes introduced in 1.5.0.
Open is at `1.3.0`. Its SDK gained coordination client methods after the
`v1.3.0` tag, but the OpenAPI contract does not describe those routes. OpenAPI
also omits two other published Core routes: per-work-item SYMBIVELA projection
and OpenCode session attachment. The README additionally states the contract
revision is `1.0.0` while the contract and release manifest say `1.3.0`.

This design makes the OpenAPI contract the complete public HTTP surface for
Core 1.7.0 and keeps the Go SDK aligned with it.

## Non-Goals

- No changes to Core or EE business logic.
- No new Core HTTP routes.
- No git tag creation, no push of tags.
- No production-readiness claim beyond recorded build and signature evidence.

## Versioning

- Repository `VERSION`: `1.7.0`.
- OpenAPI `info.version`: `1.7.0`.
- Release directory: `releases/v1.7.0/`.
- Manifest source: Core commit `47ed9ab3e84e0614725f534240cd42e70605decc`
  (`v1.7.0` plus the darwin cross-compile fix).
- Go module path remains `github.com/axisvela/coordivela-open/sdk/go/v3`.

## Contract Additions

Add these path items to `contracts/openapi/coordivela.v1.yaml`:

| Path | Methods |
| --- | --- |
| `/work-items/{id}/coordination/plan` | `GET`, `POST` |
| `/work-items/{id}/coordination/claims` | `GET`, `POST` |
| `/work-items/{id}/coordination/claims/{claimId}` | `DELETE` |
| `/work-items/{id}/coordination/findings` | `GET` |
| `/work-items/{id}/coordination/directives` | `GET` |
| `/work-items/{id}/coordination/directives/{directiveId}/outcome` | `POST` |
| `/projections/work-items/{id}/symbivela` | `GET` |
| `/work-items/{id}/attach-opencode` | `POST` |

The DELETE claim operation requires the `fencingToken` query parameter. All
work-item routes use the tenant and workspace headers already used by the other
work-item operations. POST operations require `Idempotency-Key`.

### Coordination Schemas

Add schemas matching Core JSON:

- `PlanStep`: `id`, `title`, `status`.
- `CoordinationPlan`: tenant/workspace/work-item ids, `version`,
  `expectedItemVersion` (response only), `objective`, `steps`,
  `repositories`, `paths`, `dependencies`, `evidenceRefs`, `createdAt`,
  `updatedAt`.
- `SaveCoordinationPlanRequest`: `fencingToken`, `version`, `objective`,
  `steps`, `repositories`, `paths`, `dependencies`, `evidenceRefs`.
- `CoordinationClaim`: identifiers, `repository`, `path`, `mode`
  (`read|write|execute`), `leaseId`, `fencingToken`, `expectedVersion`,
  `expiresAt`, `releasedAt`, `createdAt`.
- `AddCoordinationClaimRequest`: `fencingToken`, `repository`, `path`, `mode`.
- `CoordinationFinding`: identifiers, `kind`
  (`path_conflict|duplicate_work|dependency_not_ready|scope_drift|loop_detected`),
  `severity` (`info|warning|blocking`), `status`
  (`open|resolved|dismissed`), `evidence`, timestamps.
- `CoordinationDirective`: identifiers, `findingId`, `kind`, `status`,
  `message`, `idempotencyKey`, `authorizationRef`, `dispatchedAt`, `outcome`,
  `deliveryState`, `attemptCount`, `deliveryNote`, timestamps.
- `DirectiveOutcome`: `kind`, `note`, `recordedBy`, `recordedAt`.
- `DirectiveOutcomeRequest`: `outcome` (required), `note`.
- `SymbivelaWorkProjection`: `workItemId`, `goalRef`, `workspaceId`,
  `repository`, `state`, `ownerKind`, `ownerRef`, `version`, `updatedAt`,
  optional `coordinationPlan`, `claims`, `findings`, `evidenceRefs`.
- `AttachOpenCodeRequest`: `sessionId` (required), `fencingToken`.
- `AttachOpenCodeResponse`: `workItem`.

## SDK Additions

Extend `sdk/go/client/coordination.go` with fields already returned by Core:

- `CoordinationPlan.ExpectedItemVersion`.
- `CoordinationClaim.ExpectedVersion`.
- `CoordinationDirective.DeliveryState`, `AttemptCount`, `DeliveryNote`.

Add to `sdk/go/client/client.go`:

- `SymbivelaWorkProjection` and summary types.
- `SymbivelaWorkItemProjection(ctx, id)` calling
  `GET /v1/projections/work-items/{id}/symbivela`.
- `AttachOpenCodeSession(ctx, id, req)` calling
  `POST /v1/work-items/{id}/attach-opencode`.

## Release Artifacts

Build in a temporary staging directory, validate, then copy into
`releases/v1.7.0/`:

```text
releases/v1.7.0/
  darwin-arm64/
  linux-amd64/
  windows-amd64/
  sbom/coordivela-backend.cdx.json
  sbom/coordivela-frontend.cdx.json
  sbom/*.cdx.json.asc
  coordivela-v1.7.0-darwin-arm64.zip
  coordivela-v1.7.0-linux-amd64.zip
  coordivela-v1.7.0-windows-amd64.zip
  manifest.json
  manifest.json.asc
  SHA256SUMS
  SHA256SUMS.asc
  COORDIVELA-RELEASE-SIGNING-KEY.asc
  README.md
```

Each platform directory contains the three binaries, `NOTICE`,
`LICENSE-COORDIVELA-CORE.txt`, `SHA256SUMS`, and `SHA256SUMS.asc`.
Signing uses `.release-keys` with GPG, matching the v1.3.0 artifact style.

## Verification

1. Open SDK: `GOWORK=off go test ./...` and `go vet ./...`.
2. RuntimeAdapter example: `GOWORK=off go test ./...`.
3. Core: `go test ./...`, `go vet ./...`, `go build ./...`.
4. Parse OpenAPI with PyYAML.
5. Compare Core server `/v1` routes to OpenAPI operations; require zero
   missing operations.
6. Verify platform checksums with `sha256sum -c` or PowerShell hashing.
7. Verify every `*.asc` with `gpg --verify`.
8. Confirm each binary reports version `1.7.0`.

## Risks

- The release GPG key may require a passphrase; stop before publishing
  artifacts if signing fails.
- SBOM generation requires network access for `cyclonedx-gomod` and
  `@cyclonedx/cyclonedx-npm`.
- Full release builds require sibling repositories for local `replace`
  directives.
